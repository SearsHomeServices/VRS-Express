# 1099 Provider Portal

- **Feature flag (`ENABLE_1099_PORTAL`):** The entire portal is gated by `server/featureFlags.ts` `is1099PortalEnabled()` — default ON in development, OFF in production. To turn it on in prod: set `ENABLE_1099_PORTAL=true` in the production environment and republish (set `false` to force off anywhere). When OFF: provider login returns generic "Invalid credentials", creating a `provider_1099` account returns 403, the provider submission route returns 403, the `/tech/login` provider toggle is hidden, and the admin "1099 Provider" role option is hidden. Client reads the flag at runtime via public `GET /api/config` → `{ portal1099Enabled }` (no rebuild needed to read; flipping the server var still needs a republish in prod). The `users.company_name` column is still added on publish (harmless when gated off).
- **Role:** `provider_1099` — an admin-managed account for outside 1099 service providers, giving them a restricted version of the technician submission experience. Existing technician/agent/admin flows are unchanged (all gating is role-conditional).
- **Account model:** providers have a username (`racId`) + password (admin-set) and a preset `company_name` (nullable `varchar(120)` on `users`, ensured by `ensureProviderCompanyColumn()` — see Schema & Data Safety note about migration ordering). The company must be one of the presets in `shared/provider1099.ts` (`PROVIDER_1099_COMPANIES` / `isValidProvider1099Company`); create/update reject an invalid or missing company.
- **Login:** uses the EXISTING tech login screen (`/tech/login`) via a "VRS Auth — 1099 Provider" toggle; providers authenticate by username+password (not passwordless roster login) and redirect to the technician home. Onboarding wizards/What's-New are suppressed for `provider_1099`.
- **Restricted submission view (`tech-submit.tsx`):** hides District, removes the Warranty section, relabels "RAC ID" → "1099 Company Name" (read-only, prefilled), strips FA/AHS terms from the Infestation option wording, hides `parts_nla`, and skips the warranty lookup + matrix gate. `submission-detail.tsx` hides the warranty row; `tech-home.tsx` shows the company name; bottom nav hides Help for providers.
- **Server gating (`server/routes.ts`):** POST `/api/submissions` allows `provider_1099` but blocks `parts_nla` and **derives warranty from the service order (Snowflake) regardless of client-supplied `warrantyType`**. It rejects with a generic, non-leaking message if warranty can't be derived OR the derived warranty is Sears-family (`sears_protect`). This is the Sears-exclusion + no-leak mechanism. `lookup-warranty` returns 403 for providers.
- **History scoping:** GET list + GET `:id` scope a `provider_1099` to ONLY their own submissions; warranty is never returned to providers.
- **Drift / important behavior:** providers can submit ONLY service orders that successfully derive to an AHS / First American warranty via Snowflake. Service orders whose warranty can't be determined (e.g. Snowflake unavailable) are rejected with the same generic "isn't eligible … verify the service order number" message — by design, to avoid leaking warranty status.
